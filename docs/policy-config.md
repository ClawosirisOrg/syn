# Version 1 policy configuration

The schemas in `internal/config` and examples in `configs/` define policy validation and eligibility only; they do **not** implement webhook intake, safety preflight, review, or publication. The CLI does not yet load these files. Installation access does not activate a repository.

Service, organization and repository layers require version 1; unknown fields, duplicate keys, YAML aliases/merges, invalid identities, unsupported events/data classes and future versions fail validation. Explicit nonempty repository and event allowlists are mandatory. GitHub owner/name identities are ASCII and case-insensitive; case-variant duplicates are rejected. Empty data-class lists deny review by default. Repository profiles also define `ownership_fallback` for missing, malformed, ambiguous and unmatched trusted ownership; every omitted case refuses. The optional `approved_maintainers` mode requires a bounded explicit maintainer list and must still be verified against trusted metadata by the future resolver, not inferred from attacker-controlled branches.

The fixed event/action ceiling is `issues/opened`, `pull_request/opened`, `issue_comment/created`, `pull_request_review/submitted`, and `pull_request_review_comment/created`. Supported class labels are `public`, `internal` and `private`; the label alone grants no provider access. Forbidden GitHub mutations have no configuration representation.

`config.Resolve` intersects service, organization, profile, credential and runtime approvals. Live event intake requires all allowlists, data-class approval, service/runtime intake enablement and read credentials. `FixtureReview` is separate local non-publishing eligibility under fixture/dry-run rollout; it requires the allowlists and approved data class, but **no** GitHub credential or service intake switch. Live comments additionally require service/runtime publication enablement, issue/PR switches at each layer, an approved real runner, a healthy publisher, matching comment permission and no excess permissions. Policy booleans do not replace later checks of record validity, source-reference membership, authoritative pinned-commit provenance, target kind, marker ownership, freshness or actual isolation.

Examples are inert. Before changing them for a live repository, record owner, data-class/provider policy, retention, security escalation, credential boundaries and rollback. See [security-boundary.md](security-boundary.md).

All new Go source files carry `AGPL-3.0-or-later` SPDX identifiers. The only direct dependency added for strict YAML parsing is `gopkg.in/yaml.v3` v3.0.1; its upstream `LICENSE` identifies MIT and Apache licensing. Its source is fetched by Go modules, not copied or bundled into this repository. No generated source or bundled third-party material was added in Phase 0.
